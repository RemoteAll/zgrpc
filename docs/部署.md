# zgrpc 部署指南

本文说明把 zgrpc 服务**真正上线**要注意的事。库本身只跑 **h2c（明文 HTTP/2，prior-knowledge）**，
不实现 TLS —— 这不是偷懒，而是刻意的边界（见文末「为什么不内置 TLS」）。

## 一句话结论

> **对外一律 `nginx` / `Caddy` / `Envoy` 终止 TLS，后端用 h2c。**
> zgrpc 只监听内网/回环地址，不直接暴露公网。

## 1. nginx 反代（原生 gRPC）

```nginx
upstream zgrpc_backend {
    server 127.0.0.1:18051;
    keepalive 32;
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/api.example.com.crt;
    ssl_certificate_key /etc/ssl/api.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location / {
        grpc_pass grpc://zgrpc_backend;

        # 真实 IP 透传（服务端日志/审计用）
        grpc_set_header X-Real-IP        $remote_addr;
        grpc_set_header X-Forwarded-For  $remote_addr;

        # 默认 60s 对长流式调用偏短，按业务调
        grpc_read_timeout 300s;
        grpc_send_timeout 300s;
    }
}
```

要点：

- `grpc_pass` 会**自动处理** `te: trailers`、trailers 转发与 `grpc-timeout` 透传，
  不要写成 `proxy_pass http://`（那样会走 HTTP/1.1，gRPC 直接失效）。
- 需要 nginx ≥ 1.13.10；`http2 on;` 是 nginx ≥ 1.25 的新写法（旧版写 `listen 443 ssl http2;`）。
- 上游 `keepalive` 能显著降低建连开销（zgrpc 每连接一个线程，见第 4 节）。

## 2. Caddy 反代

```caddyfile
api.example.com {
    reverse_proxy 127.0.0.1:18051 {
        transport http {
            versions h2c
        }
    }
}
```

Caddy 自动申请证书；`versions h2c` 让上游走明文 HTTP/2。

## 3. gRPC-Web（浏览器直连）

zgrpc 本身支持 `application/grpc-web` 与 `grpc-web-text`，但它仍要求 **HTTP/2 上游**。
浏览器只能发 HTTP/1.1 或 HTTP/2 的普通请求，因此：

- **推荐**：用 **Envoy** 的 `envoy.filters.http.grpc_web` 过滤器（标准做法，兼容性最好）；
- **次选**：nginx 需要额外模块/配置，不如 Envoy 直接；
- 纯前端同域、后端同进程时，也可以让 zgrpc **直接面对浏览器**（此时反代只需普通 HTTP/2 转 h2c，
  不做协议转换），前提是浏览器侧用 `grpc-web` 客户端库并允许 `content-type: application/grpc-web*`。

CORS 需要反代或业务层自行处理（gRPC-Web 的预检请求会带 `access-control-request-headers:
content-type,x-grpc-web,...`）。

## 4. 资源与并发（重要）

zgrpc 的 `examples` 采用**每连接一个线程**（`std.Thread.spawn` + `detach`），
这在小规模内网服务上完全够用，但**必须在上层限制连接数**，否则可被打爆：

```zig
var active = std.atomic.Value(usize).init(0);
const max_conns = 512;

// accept 前判断
if (active.load(.monotonic) >= max_conns) {
    stream.close(io);
    continue;
}
_ = active.fetchAdd(1, .monotonic);
```

线程内退出时 `fetchSub`。若需要更高并发，换成固定大小的 worker 池 + 非阻塞 IO 模型（改动较大）。

## 5. 超时语义（`grpc-timeout`）

- 客户端在请求头里发 `grpc-timeout: 80m`（毫秒）之类，**服务端会解析成截止时刻**；
- handler 返回后若已过期，服务端把状态改成 `DEADLINE_EXCEEDED(4)`；
- **不会强行打断**正在阻塞的 handler —— Zig 没有抢占式取消。长耗时业务请自己埋检查点：

```zig
fn slowHandler(ctx: *anyopaque, call: *zgrpc.grpc.Call, arena: std.mem.Allocator) anyerror!void {
    _ = ctx; _ = arena;
    for (items) |it| {
        try call.checkDeadline(); // 过期即 error.DeadlineExceeded
        try process(it);
    }
}
```

- 反代侧也要给足时间：`grpc_read_timeout` / `grpc_send_timeout` 小于业务耗时会被反代先掐断。

### 客户端侧：本地读超时（0.2.1 起）

`grpc-timeout` 是「告诉服务端」；**客户端自己也要有兜底**，否则对端卡住时调用方会一直阻塞。
`Client.Options.timeout_ms` + `client.enableTimeout(stream, io)` 提供这个兜底，**Windows 同样有效**（实测 206~210ms 生效）：

```zig
var client = zgrpc.client.Client.init(gpa, &sr.interface, &sw.interface, .{
    .authority = "10.0.0.5:50051",
    .timeout_ms = 2000,
});
defer client.deinit();
client.enableTimeout(stream, io);
```

- 到点后返回 `error.Timeout`，**连接不可复用**（h2 协议状态已不完整）→ 直接丢弃重建；
- 启用后**退出时不要 `stream.close(io)`**：内部读线程可能仍阻塞在底层读上，关闭 socket 会让它拿到
  `CONNECTION_ABORTED` 而触发 std 的 panic。让进程退出时由系统回收；
- 语义是「整次调用」的时限，不是「单次读」的时限。

## 6. 健康检查

zgrpc 内置标准 `grpc.health.v1.Health`（`Check` / `Watch`），直接接 k8s / 负载均衡：

```yaml
# k8s（用 grpc-health-probe 或原生 grpc probe）
livenessProbe:
  grpc:
    port: 18051
  periodSeconds: 10
```

```bash
# 命令行验证（需 grpcurl）
grpcurl -plaintext 127.0.0.1:18051 grpc.health.v1.Health/Check
```

`Watch` 在本库的同步模型下**默认只推一次当前状态**（`health.Service.opts.watch_pushes`），
适合探针，不适合长订阅。

## 7. 上线自检清单

- [ ] 服务只监听 `127.0.0.1` 或内网地址，公网入口只有反代
- [ ] 反代用 `grpc_pass`（nginx）/ `h2c`（Caddy），不是 `proxy_pass http://`
- [ ] `max_concurrent_streams`（默认 100）、`max_header_block`（默认 64 KiB）、
      `max_body`（默认 4 MiB）按业务调过，没有留默认值裸奔
- [ ] 连接数上限已加（见第 4 节）
- [ ] 反代的读写超时 ≥ 业务最长耗时
- [ ] 健康检查已接（k8s probe / LB）
- [ ] 日志级别与脱敏策略确认（本库用 `std.debug.print`，生产建议在业务层接自己的日志）

## 8. 为什么不内置 TLS

查过 Zig 0.17 标准库：`std.crypto.tls` **只有客户端实现，且没有 ALPN 扩展**。
这意味着：

1. 服务端 TLS 要自己实现 TLS 1.3 握手（证书链校验、密钥交换、会话恢复…），
   工作量与维护成本远超一个传输层库应有的范围，且一旦写错就是安全问题；
2. 即使硬做，没有 ALPN 也无法与标准 gRPC 客户端协商 `h2`，等于白做。

业界的通行做法就是**TLS 终止在反代**（这也是 gRPC 官方文档推荐的部署形态之一），
zgrpc 遵循同一约定：**你负责反代，我负责协议**。
