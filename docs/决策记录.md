# zgrpc 决策记录

## 2026-11-12：gRPC 独立成库（不放进 zzig）

- **用户原话**：「Rust 我记得有库可以直接复用的？Zig 是否有库可以直接复用？」→
  「那是不是也可以单独弄个 Zig Grpc 的库的？不直接放在 zzig 中？」。
- **调研结论（实测元数据，非印象）**：
  - Rust 侧确实现成：`h2`（本机 cargo 缓存已有 `h2-0.4.20`）、`hyper`、`tonic`，直接复用即可；
  - Zig 侧**没有可直接复用的零依赖 gRPC 库**：`grpc-lite` 依赖 nghttp2(C)/mbedtls/c-ares/zio 等 13 个；
    `http2.zig` 只有 h2 且依赖 boring/turboapi-core；`nilo` 是整套框架；`zaxified/zig-libs` 零依赖但无 gRPC；
  - **Zig 标准库只有 HTTP/1.1**：`lib/std/http` 下仅 `Server.zig`/`Client.zig`/`HeadParser.zig`/`ChunkParser.zig`，
    全量搜 `hpack|:authority|:scheme` 零命中 → h2/HPACK 必须自建。
  - `zig fetch` 在本机报 `TlsInitializationFailed`（Steam++ 中间人证书），第三方包能否编译**未能实测**，
    这一点如实记录，不当作「已排除」。
- **决策：独立成库 `zgrpc`，zzig 不内置 gRPC**。理由：
  1. 体量与受众：h2+HPACK+gRPC 是整套协议栈，只有需要 gRPC 的项目才该付出这份成本；
  2. 依赖方向干净：zgrpc 零依赖（只用 std），不依赖 zzig；将来 zzig 要集成，以「可选依赖 + 薄适配」引入；
  3. 可替换：便于与生态内其它 h2 实现做对照测试，也便于整体替换而不是深挖耦合。
- **同时从 zzig 迁出**：上一轮已写进 `zzig/src/http/hpack.zig` + `hpack_huffman_table.zig` 的两份文件
  **已删除**（zzig 无其它引用），代码整体迁到 `zgrpc/src/`，避免「同一实现两处」。
- **关键实现取舍**：
  1. **HPACK Huffman 表用脚本生成**（从规范同源数据抽取，256 项零手误），不手抄 —— 手抄 256 项必然出错；
  2. **HPACK 解码完整、编码简化**：解码必须支持 Huffman（所有主流 h2 客户端都会编码），
     编码侧服务端每次只有几个响应头，不值得再维护 Huffman 编码表；
  3. **HPACK 叶子编码用 `-2 - sym`**：最初用 `-1 - sym`，与「空槽 = -1」冲突（sym 0 时撞车），
     会导致非法码被当成合法解出；改用 `-2 - sym` 并把 EOS(256) 排除出树，命中即报 `InvalidHuffman`；
  4. **h2 v1 串行**：一条连接同一时刻一个流，并发新流回 `RST_STREAM(REFUSED_STREAM)`
     （该码语义是「未处理」，客户端可安全重试）；gRPC unary 串行调用完全够用；
  5. **收到 DATA 立即回补窗口**（连接级 + 流级），否则对端窗口耗尽会卡死；
  6. **读帧 EOF 视为正常收尾**：`Reader.readSliceAll` 在 EOF 报 `EndOfStream`（不是 `ReadFailed`），
     最初按 `ReadFailed` 判定导致连接结束被当异常抛出 —— 已改为打印原因后返回 `ConnectionClosed`。
- **验证（实测）**：
  - `zig build test --summary all` → **13/13 tests passed**，exit 0。覆盖：
    HPACK（RFC 7541 C.4.1 请求 + C.6.1 响应含动态表、往返、尺寸更新、非法 Huffman 尾部/EOS）、
    h2（preface + SETTINGS + HEADERS/DATA 端到端断言响应帧齐全、PING ACK 同 payload、DATA 回补窗口）、
    gRPC（unary 端到端断言 `grpc-status=0` 与响应消息、未注册方法回 `UNIMPLEMENTED(12)`）；
  - **真实 socket 实测**：`echo-server` + `echo-client` → 客户端 `grpc-status=0 响应=hello-grpc`、exit 0，
    服务端日志 `收到 10 字节：hello-grpc`；随后连接 `EndOfStream` 正常收尾。
  - 端口踩坑：50051 已被本机 PID 5236 占用（bind 报 `ACCESS_DENIED`），示例改用 18051。
- **未做**：TLS/ALPN、并发流、压缩、客户端流/bidi 背压、protobuf codegen、断点/Range。
- **待装备**：接续基建（`.github/copilot-instructions.md`、`tools/continuity/`）尚未铺，可后续从任一已装备仓库复制。

## 2026-11-12 增补（二）：h2 改为多路复用（去掉「并发流直接拒绝」）

- **用户原话**：「zgrpc继续帮我推进」。
- **推进理由（实际短板）**：v1 是「一条连接同一时刻一个流，并发新流回 `RST_STREAM(REFUSED_STREAM)`」。
  gRPC 客户端（grpc-go/grpc-java/grpc-dotnet）会在一条连接上并发发起调用，虽然该错误码可重试，
  但等于把客户端逼成串行 —— 这是从「demo 能跑」到「能用」的关键差。
- **改动**：
  1. `StreamState` **自带 arena**（`std.heap.ArenaAllocator`）+ 每流 `send_window`；流结束整体释放，
     多流并存时不会因连接级 arena 的 reset 时机互相污染；
  2. `Connection.streams: ArrayListUnmanaged(*StreamState)` 取代单流字段，`findStream/createStream/destroyStream`；
  3. 帧处理统一为 `handleFrame(hdr, payload)`（payload 先读出再分发）；
  4. **发送受流控阻塞时的业务帧进 `pending` 队列**（延后到主循环处理），不再像 v1 那样当场 `REFUSED_STREAM`；
  5. 收到对端 `SETTINGS_INITIAL_WINDOW_SIZE` 变化时，按**差值**调整所有现存流的发送窗口（RFC 9113 §6.9.2）；
  6. 我们自己的 SETTINGS 现在声明 `MAX_CONCURRENT_STREAMS`（默认 100）与 `INITIAL_WINDOW_SIZE`；
  7. handler 嵌套深度上限 4（发送阻塞 → 读帧 → 又派发新请求 → 再阻塞 的递归保护），超限回 `REFUSED_STREAM`。
- **保留的简化**：handler 仍是**同步串行执行**（一次跑一个流的业务），只是接收侧多路复用。
  真正的并行执行需要多线程 + 共享写锁，本轮不做（也用不上：unary 处理通常微秒级）。
- **验证（实测）**：
  - `zig build test --summary all` → **14/14 tests passed**，exit 0；
    新增用例「多路复用（两个流交错收头/收体，各自独立响应）」：两条流 `:status 200` 各一个、
    body 分别为 `one`/`three`、两条都 `END_STREAM`、**无 `RST_STREAM`**；
  - **真实 socket 并发双流**：`echo-client` 在同一条 TCP 连接上先发两条 HEADERS 再发两条 DATA，
    两个流分别拿到 `grpc-status=0` 与 `stream-one`/`stream-three`，exit 0；
    服务端日志 `收到 10 字节：stream-one` / `收到 12 字节：stream-three`。
- **未做**：TLS/ALPN、优先级、handler 并行、压缩、客户端流/bidi 背压、protobuf codegen。

## 2026-11-12 增补（四）：gRPC 完善度盘点 + 新增客户端库 `zgrpc.client`

- **用户原话**：「zgrpc中grpc相关的功能全部完善了么？是不是可以直接同步zig同类项目的代码来实现」。
- **盘点结论：未完善**。已具备：16 个状态码 / 长度前缀分帧 / unary / 服务端流式 / 路由 / `grpc-status` 走 trailers。
  缺失：客户端流与 bidi、压缩（`grpc-encoding`）、`grpc-timeout`、metadata `-bin`（base64）、
  `grpc-message` percent-encoding、最大消息尺寸、interceptor、健康检查/反射、protobuf codegen、TLS/ALPN、客户端库。
- **「直接同步同类项目代码」实测评估（否决）**：
  | 项目 | 许可证 | 实测 | 结论 |
  |---|---|---|---|
  | `ziglana/gRPC-zig` | Unlicense | `src` 合计 ~20KB（server.zig 3.8KB / client.zig 2.7KB / transport.zig 6.3KB），源码里仍是 `// TODO: Implement proper method routing based on request headers`，鉴权是硬编码 `secret_key` | **搬过来是倒退**（功能少于 zgrpc） |
  | `fanyang89/grpc-lite` | MIT | `channel.zig` 470KB、`server.zig` 326KB、`frame.zig` 20KB；h2 交给 **nghttp2(C)**，另带 mbedtls / c-ares / zio / libxev / protobuf / gperftools | 搬进 = **破坏零依赖**；要用就当独立项目依赖 |
  | `hendriknielaender/http2.zig` | MIT | 只有 h2（依赖 boring TLS + turboapi-core） | 只能参考 h2，而本库 h2 已有 RFC 向量 + 端到端验证 |
  | `nevindra/nilo` | MIT | 33MB 整套框架（zio/pg.zig/zqlite/tls.zig/llhttp/zstd） | 无法拆分 |
  → 真正可复用的只有「规范表/算法」（HPACK Huffman 表等，本库已脚本生成 + RFC 7541 向量验证），
  以及 `grpc.health.v1` / reflection 的 **.proto 定义**（不是代码问题）。
- **本轮改动：新增 `src/client.zig`（gRPC 客户端库）** —— 在此之前 zgrpc 只有服务端，连自测都要手写帧：
  1. `Client.handshake`（preface + SETTINGS）、`unary`、**`callMany`（同一连接并发多条流）**；
  2. 按 `stream_id` 归位响应，自动 `SETTINGS/PING` 回 ACK、`DATA` 后回补窗口；
  3. `Result.{stream_id, status, message, messages, aborted}` + `ok()`；
  4. `examples/grpc_echo_client.zig` 由 200 行手写帧改为 ~45 行库调用，**并发双流验证保留**。
- **验证（实测）**：
  - `zig build test --summary all` → **17/17 tests passed**（新增 3 个客户端用例：unary 解析、
    并发两流按 id 归位、非 0 状态码不算 ok），exit 0；
  - `tools\regression.ps1` → 构建 PASS / **tests 17（下限已抬高到 17）** / 冒烟 PASS（库化客户端并发双流），exit 0。
- **下一步（未做，按价值排序）**：客户端流/bidi → 压缩（`std.compress.flate`，仍零依赖）→

## 2026-11-12 增补（五）：补齐客户端流 / bidi（四项流式全支持）

- **用户原话**：「请继续」（承接上一轮排序：客户端流/bidi → 压缩 → grpc-timeout → …）。
- **改动**：
  1. **h2 层新增流式模式** `Connection.serveStreaming(StreamHooks)`：
     `onHeaders` 在请求头就绪时回调一次，`onData` 在**每个 DATA 帧到达时**立即回调（不再攒到 END_STREAM），
     新增 `onReset` 通知；`serve`（整请求模式）行为保持不变。
  2. **grpc 层新增 `StreamRoute`**（`path` + `on_message` + `on_end`）与 `Server.streamHooks()`：
     内部按 gRPC 长度前缀**跨 DATA 帧重组**，业务每条完整消息回调一次，可在回调里随时
     `call.sendMessage`（即 bidi）；流式模式下**同时兼容整请求路由**（unary/服务端流式自动累积到 END_STREAM）。
  3. **客户端新增 `Client.clientStream(method, messages)`**：批量客户端流/bidi —— 多条请求消息一次性发完，
     收全部响应消息。
  4. 示例：服务端加 `/echo.Echo/Chat`（每条消息即时回 `chat:<msg>`），客户端加一次 3 条消息的 bidi 调用。
- **踩坑（段错误，值得记住）**：最初 `Responder` 建在 `afterHeaders` 的**栈**上却存进 `Call` 跨回调使用，
  第二次回调时 `self.rsp.stream` 已是栈垃圾 → `Segmentation fault at address 0x10`（崩在
  `Responder.begin` 的 `stream.allocator()`）。正解：流式模式下 `Responder` 用 `流的 arena` 分配
  （`s.rsp: ?*Responder`），生命周期与流一致。
- **验证（实测）**：
  - `zig build test --summary all` → **19/19 tests passed**（新增 2 个用例：
    「bidi 流式（每条消息即时响应 + 跨 DATA 帧重组）」——把第 2 条消息**切成两帧**发送，验证重组；
    「流式模式下整请求路由仍可用」），exit 0；
  - **真实 socket**：`echo-client` → unary 并发双流 `grpc-status=0`；**bidi 3 条请求 → 3 条响应**
    （`chat:a` / `chat:b` / `chat:c`），exit 0；
  - `tools\regression.ps1` → 构建 PASS / **tests 19（下限已抬到 19）** / 冒烟 PASS，exit 0。
- **当前 gRPC 能力矩阵**：unary ✅ / 服务端流式 ✅ / 客户端流 ✅ / bidi ✅（四项齐全）。
  仍缺：压缩、`grpc-timeout`、metadata `-bin`、`grpc-message` percent-encoding、
  最大消息尺寸（仅整体上限）、interceptor、健康检查/反射、protobuf codegen、TLS/ALPN。
## 2026-11-12 增补（六）：gRPC-Web 支持 + Rust 双向对拍工具

- **用户原话**：「像这个是不是得Rust写一个服务端和客户端来方便调测zig的Server和Client，尤其要考虑支持grpc web」→「edition 现在都上2024吧」→「git要过滤」。
- **为什么要做这件事**：只用自己的客户端测自己的服务端，是「自己错自己对」；用成熟实现当裁判才有说服力。
- **改动 1：zgrpc 支持 gRPC-Web（服务端侧）**
  - `content-type` 识别新增 `application/grpc-web*`（必须先判 web：它也以 `application/grpc` 开头）；
  - 响应 `content-type: application/grpc-web+proto`，**trailers 编码成 body 尾帧**（`0x80 | 4B 长度 | "k: v\r\n"`），
    用新增的 `Responder.endData()` 以 DATA(END_STREAM) 收尾，而不是 HTTP trailers；
  - 原生 gRPC 路径行为不变。`application/grpc-web-text`（base64）**未做**。
- **改动 2：Rust 双向对拍工具 `tools/interop-rust/`**（hyper 1.x + h2c，**不参与 zig build**）
  - `server`：Rust gRPC 服务端（unary 回显 + bidi）→ 用来测 **zgrpc 的客户端**；
  - `client [--web]`：Rust gRPC / gRPC-Web 客户端 → 用来测 **zgrpc 的服务端**；
  - 不依赖 protobuf（payload 即原始字节，与 zgrpc 设计一致）；`edition = "2024"`。
- **git 过滤**：`.gitignore` 增加 `tools/interop-rust/target/` 与 `build.log`（`git check-ignore` 已验证生效）。

  3. zgrpc client → **Rust server**：unary 并发双流 `stream-one`/`stream-three`、bidi `chat:a/b/c`，exit 0；
  4. `zig build test` → **20/20**（新增 grpc-web 尾帧用例），`regression.ps1` 下限抬到 **20**。
- **未做**：`grpc-web-text`（base64）、压缩、`grpc-timeout`、metadata `-bin`、健康检查/反射、codegen、TLS。
## 2026-11-12 增补（七）：gRPC 消息压缩（grpc-encoding: gzip）

- **用户原话**：「请继续，然后做审计修复并继续推进zgrpc」。
- **背景**：上一轮盘点出的缺口里，「压缩（`grpc-encoding`）」是真实场景最容易遇到的（大消息跨网/跨机器）。
- **改动**：
  1. 新增 `src/gzip.zig`（零依赖，走 `std.compress.flate`）：`compress` / `decompress`，服务端与客户端共用一份；
  2. **接收侧自动解压**：`MessageIterator` 增加 `alloc`，压缩消息（帧标志位=1）自动解压后再交给业务；
     未提供 `alloc` 时压缩消息返回 `null`（宁可不给，也不把压缩字节当明文塞给业务）；
     所有构造点（`Call.firstMessage` / `Call.messages`）都带上流的 arena；
  3. **发送侧协商压缩**：`describeContentType` 解析 `grpc-accept-encoding`，`Call.sendMessage` 在
     「客户端接受 + 消息 ≥ 256 字节」时压缩并置帧标志位，首帧额外带 `grpc-encoding: gzip`；
  4. 阈值与 zzig / DH.RustBase 统一为 **256 字节**（小报文压完反而变大）。
- **踩坑**：`"..." ** 8` 数组重复运算符在 Zig 0.17 已移除（`binary operator '*' has whitespace on one side`），

本轮用「常驻读线程 + `io.waitTimeout`」把它做成了，Windows 实测 **206~210ms** 生效。

### 为什么这条能成

前六条路（见增补十六）都试图**打断一个已发出的同步读**，而 Zig 0.17 的 AFD 读不可打断、取消还会崩进程。
换思路：**不打断读，而是让「等待数据」这一侧有超时**。

- 读线程：`io.operate(.net_read)` 循环把 socket 数据读进 16 KiB 临时区 → 加锁 push 进缓冲 → `cond.signal`。
  它自己阻塞是**可接受的**（daemon 语义，不影响调用方）。
- 调用方：`io.waitTimeout(io, &mutex, deadline_ns - now)` —— 底层是 futex / `WaitOnAddress`，
  **跨平台且有真超时**，不依赖 socket 能否被中断。

### 实现

- 新增 `src/async_reader.zig`：`start(alloc, io, stream)` / `readExact(dest, deadline_ns)` / `tryDestroy()` / `isFinished()`。
  读线程遇到错误或 EOF 调 `finishWith(err, eof)`；`readExact` 在缓冲不足时按剩余时间 `waitTimeout`，
  超时返回 `error.Timeout`。
- `client.Client` 新增 `async_reader` 字段：`enableTimeout(stream, io)` 起读线程，`readExact` 改走 AsyncReader；
  `startGuard(reqs)` 取**所有请求 timeout_ms 的最小值**折算成绝对截止时刻 `deadline_ns`，`stopGuard()` 清除。
- 三处读路径（`unary` / `callMany` / `clientStream`）的错误映射统一走 `mapReadError()`：
  `error.Timeout` 原样上抛，其它映射为 `error.ConnectionClosed`。
  —— 这一步最初漏了：探针实测 206ms 时确实触发了超时，但被 `catch` 兜成 `ConnectionClosed`，
  看起来「没生效」。**这也说明探针必须断言具体错误，不能只看「有没有退出」**。

### 使用约定（必须写进文档，否则会踩 panic）

- 启用本地超时的连接，**退出时不要 `stream.close(io)`**：读线程可能仍阻塞在底层读上，
  关闭 socket 会让它拿到 `CONNECTION_ABORTED`，而 std 对「读已关闭的 AFD 句柄」返回的正是这个错误 → `unexpectedStatus` panic
  （本轮实测踩到）。让 OS 在进程退出时回收即可。
- 超时后的连接**不要复用**（h2 协议状态已不完整），重新建连。
- `Client.deinit()`：读线程已自行结束 → `tryDestroy()` 完整回收（join + free）；
  仍阻塞 → 只置 `stop` 标志，**不 join 也不释放**——泄漏一个有界结构，换「绝不 hang、绝不 use-after-free」。

### 追问：不依赖 socket 被中断，会不会一直占用线程？（2026-11-12 用户原话）

用户原话：**「不依赖 socket 能否被中断  会不会一直占用线程？」**

**会短期占用，但不会永久泄漏** —— 这是实测结论，不是推断。探针加了三段断言：

```
① 超时生效：207ms 后返回 error.Timeout（设定 200ms）
② 超时后读线程状态：仍在（阻塞在底层读上，Windows 不可打断）
③ 对端关闭后读线程已退出并完整回收
```

- 超时那一刻线程**确实**还卡在 `io.operate(.net_read)` 里（AFD 读不可打断，这是事实，不粉饰）。
- 但只要对端**关闭连接**（→ `data_len == 0`，走 `finishWith(eof)`）、**发来数据**（→ 循环回顶部检查 `stop`）、
  或**网络报错**，线程就自行退出。
- 真正会滞留的只有「对端既不关连接也不发数据」（黑洞 / 半开）—— 这时要等 TCP keepalive 或网络层报错。

### 为此做的两项最小化（不改变语义）

1. **线程栈压到 256 KiB**：`std.Thread.SpawnConfig.default_stack_size = 16 * 1024 * 1024`（源码实测），
   读线程只用 16 KiB 临时区 + 少量调用栈，显式 `.stack_size = 256 * 1024`。
   滞留代价从「16 MiB 虚拟地址」降到「256 KiB」。
2. **`deinit` 变成「尽力回收」**：先 `tryDestroy()`（线程已结束则 join + free）；否则 `shutdown(.both)` ——
   **唤不醒挂起读**（增补十六第 6 条已实测），但**不会像 `close` 那样触发 panic**，且能让「下一次读」
   立即失败退出；随后最多等 50ms，能回收就回收。只有真卡在 read 里才保留结构。

补充一句口径：这部分占的是**虚拟地址 + 提交内存，不占 CPU**（阻塞在 IO 上，不是轮询）。
每个 `Client` 最多一条读线程（`enableTimeout` 幂等）；超时后连接不复用，别对同一 `Client` 反复重试。

### 源码给出的四个事实（都带位置）

1. `lib/std/Io/Threaded.zig` 的 `netReadWindows` 发起读时**已经是 AFD overlapped 模式**：
   `.AfdFlags = .{ .NO_FAST_IO = true, .OVERLAPPED = true }`；

4. `IpAddress.ConnectOptions` 有 `timeout: Io.Timeout = .none` 字段，但 Windows 分支是

### 三次实测（每次只改一个变量）

| 尝试 | 结果 |
|---|---|
| `IOCTL_AFD_SOCKOPT` 设 `SO_RCVTIMEO` | **`STATUS_NOT_SUPPORTED (0xC00000BB)`** —— `SO_RCVTIMEO` 是 Winsock 层概念，AFD 不认 |

### 一、HPACK Huffman 编码（规范完整性）

### 二、基准跑出真缺陷：没关 Nagle（TCP_NODELAY）

新增 `tools/bench.zig`（`zig build bench -Doptimize=ReleaseFast`）：
单连接复用、服务端与客户端同进程不同线程、128 字节回显、预热 200 次、报告 QPS 与 p50/p95/p99。

**第一次跑就发现异常**：p50 = 282us，但 **p95 = 14.7ms**，且加诊断后看到「慢调用随机分布、无固定周期」（118/800 次 > 5ms）。

定位与验证（每次只改一个变量）：

| 状态 | QPS | p50 | p95 | >5ms 占比 |
|---|---|---|---|---|
| 系统默认（Nagle 开） | 427 | 328 us | **14708 us** | 10.7% |
| `TCP_NODELAY = 1` | **4762** | **168 us** | **382 us** | 0.14% |

- **QPS ×11，p95 ÷38**。
- 机理：gRPC 一次调用是 HEADERS + DATA + TRAILERS 多个小包；Nagle 要求「前一个小包被 ACK 前不发下一个小包」，
  与对端延迟 ACK 叠加即产生 10~200ms 随机尖峰。**所有官方 gRPC 实现都默认关 Nagle**，我们漏了。
- 实现：`zgrpc.socket_timeout.setNoDelay`，Windows 走 `IOCTL_AFD_SOCKOPT`（`IPPROTO_TCP` / `TCP.NODELAY`，
  与 `SO_RCVTIMEO` 不同，**这个 AFD 是支持的**），POSIX 走 `setsockopt`。

**默认化**（不能只留在基准里）：
- `Client.enableTimeout(stream, io)` 内自动关闭 Nagle；
- 新增 `Client.tuneSocket(stream, io)`，不启用超时也能单独调；
- 服务端在 accept 后调 `zgrpc.socket_timeout.setNoDelay`，`examples/grpc_echo_server.zig` 与 `tools/bench.zig` 已示范；
- README 新增「性能」章节，写明数字、对比表与「必须关 Nagle」的理由。

## 2026-11-12 增补（二十）：zio 后端对照 —— 实测「std 方案不输异步运行时」

用户问：「lighting 是不是也用的异步？」「如果我们的方案接近 zio 的就用自己的，否则应该作为默认运行时」。

### 事实：lighting 用的是 std 的结构化并发，不是 zio

`lighting/src/server.zig` 第 1 行：*"HTTP server implementation powered by Zig structured concurrency (`std.Io.Group`)"*，
源码里是 `self.group.concurrent(self.io, serveConnWorker, .{ self, stream })`；
`lighting/build.zig.zon` 的 `dependencies = .{}` —— **框架本体零依赖**。
`zio` 只出现在 `bench/zig/build.zig.zon`，是基准的可选后端（`IO=zio|std`）。
它的 741k QPS 是 **Linux + io_uring + 18 核 + wrk 50 并发**，与 gRPC unary 不可直接比。

### zio 是什么（读官方 README）

- 平台：**Linux `io_uring`（退化 `epoll`）、Windows `IOCP`、macOS/BSD `kqueue`、其它 `poll`**；
- **完整实现 `std.Io`**：「Zig 0.17 code written against std.Io runs on zio unmodified」；
- MIT；协程（stackful）+ work-stealing executor。

这意味着：**zgrpc 不需要引依赖，只要处处走 `io` 参数，调用方传 `rt.io()` 就能获得真异步**。
为此把唯一绕过 `io` 的地方改了（`client.readExact`）：
先用 `io.operateTimeout(net_read)`，后端报 `ConcurrencyUnavailable`（std Threaded 就这样）时才回退平台原生方案（Windows AFD overlapped / POSIX `SO_RCVTIMEO`）。

### 实测：Windows 上 std 方案**不输** zio

新增 `examples/with-zio/`（独立工程，自带 `build.zig.zon` 引 zio，不动主库依赖），同一份 zgrpc 服务端 + 客户端，只换 `Io` 实例：

| 并发连接 | std（每连接一线程 + 原生 AFD） | zio（协程 + IOCP） |
|---|---|---|
| 1 | **4762** QPS / p50 168us | 2502 QPS / p50 238us |
| 4 | **13221** QPS | 10401 QPS |
| 16 | **23268** QPS | 21761 QPS |
| 64 | **20629** QPS | 20467 QPS |

规律：**并发越高差距越小（1.9x → 1.01x），但始终没反超**。

原因（不猜，按机理）：
1. 单连接/低并发下，协程调度是**纯开销**，没有任何等待可以「省」——我们每次 unary 的瓶颈是 HPACK + 帧处理，
   IO 等待占比很低，异步换不来收益；
2. 本测试服务端与客户端**同进程抢同一批 CPU**，没有额外核留给事件循环；
3. Windows 的 zio 走 IOCP，其相对收益不如 Linux 的 io_uring（lighting 的 +48% 是 io_uring 的成绩）。

### 外部工具验证（ghz）

自己写的客户端与自测服务端同进程，说服力有限。装了 Go 的 `ghz`（gRPC 压测的业界标准）作独立进程压测：

```
Requests/sec: 10451.79 | Average 1.76ms | p50 2.00ms | p95 3.00ms | p99 3.51ms | 6000/6000 OK
```

与我们自测的 4 连接 13221 QPS 同量级，互相印证。

### 结论与口径

- **默认保持 std（零依赖）**：Windows 实测全场景更快，且没有额外依赖风险；
- **zio 作为可选后端**：`examples/with-zio/` 已给出完整用法；Linux 上是否反超需在 Linux 机器上用 ghz 复测（本机无法验证，不写结论）；
- **单线程场景**：std 服务端目前是「每连接一线程」；单线程/嵌入式场景需要另做（单 accept 循环 + 非阻塞读），列为后续项；
- 顺带补了 `.gitignore`（`zig-out/`、`.zig-cache/`、子工程缓存、`artifacts/`、`*.log`）。

## 2026-11-12 增补（二十一）：基准测试的**方法论局限** —— 单机测不出真实结果

用户问：**「是不是得多机测试才能测试出真实的结果」**。答案是**对**，而且本轮实测撞到了墙。

### 单机测试的两种方式与实际数字

| 方式 | 数字 | 性质 |
|---|---|---|
| 自测（客户端+服务端同进程） | 16 连接 **23,268 QPS** / p50 168us | 乐观上界：两端抢同一批 CPU，客户端开销被低估 |
| `ghz` 独立进程，两端各绑 6 核 | 20 并发 **4,525 QPS** / p50 4.01ms | 客户端（Go+gRPC 栈）可能本身就是瓶颈 |
| `ghz` 200 并发，不绑核 | 4,147 QPS / p50 44.87ms | 同上 |
| `ghz` 200 并发，服务端绑 6 核 | 2,561 QPS / p50 61.63ms | 核数不足时更差 |

### 关键推断（Little's Law 自洽，不是猜）

- 20 并发 ÷ 4.36ms = **4,587**，实测 4,525；
- 200 并发 ÷ 44.87ms = **4,458**，实测 4,147；
- 200 并发（绑核）÷ 75.72ms = **2,641**，实测 2,561。

三种配置的理论与实测都吻合，且**都撞在约 4,500 QPS** —— 说明限制来自**同一个非服务端因素**（`ghz` 客户端 / loopback 协议栈），而不是 zgrpc 的处理能力。
绑核反而更慢（4,525 → 2,561）也印证：限制在客户端与可用核数，不在服务端。

### 结论与待办

- **单机数字只能做相对比较**（例如「关 Nagle 前后差 11 倍」「Huffman 省 25.8%」这类同条件对照是可信的）；
- **绝对吞吐必须多机测**，且必须同时记录压测机 CPU（< 80% 才说明客户端不是瓶颈）；
- zio / `io_uring` 的优势在 Windows 单机上无法验证，需要在 Linux 机器上复测；
- 已把这些方法论写进 README「测试方法与局限」，避免以后拿错数字下结论。

### 顺带

`tools/bench.zig` 的 `--conns` 去掉了固定 64 上限（改为动态分配），实测到 512 连接全部成功（10,647 QPS）。**64 从来不是库的限制**，只是基准工具里数组的大小。

### 踩到的真缺陷：enum 字段被编成 message

第一版 `describe` 直接失败：

```
cannot resolve type: resolved "echo.Status", but it is not an message
```

- **原因**：`fieldTypeOf` 把 `named` 一律映射成 `TYPE_MESSAGE(11)`，而 `echo.proto` 里

2. **`TIME_WAIT` 被误判为占用**：`Get-NetTCPConnection -LocalPort X` 会连 `TIME_WAIT` 一起返回，补 `-State Listen`。
3. **PowerShell 吞掉 JSON 引号**：`-d '{"value":3}'` 传给原生 exe 会变成 `{value:3}`（`invalid character 'v'`）。

## 2026-11-13 增补（二十五）：`repeated` 放开到任意元素（并顺手修掉 packed 编码的类型陷阱）

用户原话：「请继续」。上一轮盘点里 ① 是「proto3 codegen 子集补全」，本轮先做其中**最常用、且此前直接报错**的一项。

### 现状问题（不是「没做」，是「做错了」）

- `repeated` 只允许数字标量：`repeated string tags = 1;` 直接报 `不支持`；
- 更严重的是 packed 编码**按字段类型选错了函数**：`repeated float/double/fixed32/fixed64` 全走
  `packedUint64`（varint），而 protobuf 规定它们是**定长小端**（4/8 字节）。这类错误不会报错，
  只会让对端解析出垃圾——**静默错**比报错更糟。
- 生成器里 `repeated int64` / `repeated uint32` / `repeated bool` 会因为 `packedUint64` 签名是
  `[]const u64`、`packedInt32` 是 `[]const i32` 而**编译失败**（只是 echo.proto 恰好只用到 int32/uint64，没暴露）。

### 改法

1. **`pb.Writer` 加四个泛型 packed 写入口**（`anytype` + `std.meta.Elem` 按元素类型分派）：
   | 方法 | 适用 | wire |
   |---|---|---|
   | `packedVarint` | int32/int64/uint32/uint64/bool | varint |
   | `packedSint` | sint32/sint64 | zigzag varint |
   | `packedFixed32` | float/fixed32/sfixed32 | 4 字节小端 |
   | `packedFixed64` | double/fixed64/sfixed64 | 8 字节小端 |
   原来两个固定签名（`packedUint64` / `packedInt32`）保留，避免破坏既有调用。
2. **`pb.Field` 加 `packedFixed32s` / `packedFixed64s`**：解析定长 packed 载荷（长度不是 4/8 的倍数
   直接报 `InvalidVarint`，不静默截断）。
3. **生成器改为「局部 list 累积」**：
   ```zig
   var lst_tags: std.ArrayListUnmanaged([]const u8) = .empty;
   ...
   while (r.next()) |f| switch (f.number) {
       8 => try lst_tags.append(a, f.asBytes()),
       4 => if (f.wire == .len) {
               for (try f.packedVarints(a)) |v| try lst_samples.append(a, ...);
           } else { const v = f.value; try lst_samples.append(a, ...); },
       else => {},
   };
   self.tags = lst_tags.items;
   ```
   - **同时接受 packed 与非 packed**（对端写 `[packed=false]` 也能解）——此前只认 packed，
     非 packed 会被当成空载荷丢掉；
   - 同号字段重复出现会**累积**而不是覆盖（此前是直接赋值）；
   - 顺带删掉一段写了却没用的 `var tmp: [16]u32 = undefined;`。

### 为什么 `oneof` 在 Zig 里反而简单

protobuf 的 oneof 语义是「同时只能设置一个成员」，**这正是 Zig 的 tagged union**：

```zig
pub const Payload = union(enum) {
    text: []const u8,
    rich: BumpResponse,
};
payload: ?Payload = null,
```

不需要额外的 `case` 字段或手写互斥检查 —— 编译器保证。

### 落地

| 侧 | 改动 |
|---|---|
| 解析 | `Field.oneof_index: ?u32` + `Message.oneofs: []const []const u8`；`parseMessage` 识别 `oneof name { ... }`，内部成员拒绝 `repeated` / `map`（protobuf 规定） |
| 代码生成 | 每个 oneof 生成一个 `union(enum)` 类型 + `?Union` 字段；encode 走 `if (self.x) |c| switch (c) { ... }` |
| 服务反射 | `DescriptorProto.oneof_decl = 8`（`OneofDescriptorProto.name = 1`）+ `FieldDescriptorProto.oneof_index = 9` |

### 关键语义差异：oneof 成员不能「零值不写」

普通 proto3 字段的默认值不序列化；但 oneof 成员**一旦被显式设置就必须写**，
否则接收方无法区分「设成空串」与「没设置」。

为此把「单值写入」抽成 `writeValueStmt`（不带 `!= 0` 判断），与 `writeEncodeField`（带判断）分开。
测试专门覆盖了这条：`payload = .{ .text = "" }` 编码后长度 > 0，解码回来 `payload != null`。

### 顺带抓到的真缺陷：enum 默认值被写进报文

写上面这条测试时（`echo.Summary{}` 编码应为 0 字节）失败，查出生成器旧逻辑是：

```zig
if (self.status) |v| try w.enumField(2, v) else try w.enumField(2, Status.UNKNOWN);
```

**`null` 时反而写了一个 0**。proto3 的默认值本就不该序列化，改成一个条件
`if (self.x) |v| { if (@intFromEnum(v) != 0) try w.enumField(N, v); }`。

这个缺陷之前一直没暴露，是因为 `BumpRequest`（空消息测试用的类型）没有 enum 字段，
而枚举测试只断言往返值不断言字节数 —— **「往返一致」不能替代「编码最小」**。

## 2026-11-13 增补（二十八）：`optional` 打通 —— proto3 显式 presence（含合成 oneof）

### 语义要点：`optional` 与普通字段的编码规则**相反**

| 场景 | 普通字段 | `optional` 字段 |
|---|---|---|
| 未设置 | 不写 | 不写 |
| 设为 0 / 空串 | **不写**（默认值不序列化） | **必须写**（否则无法区分） |

所以生成侧特意把「单值写入」抽成 `writeValueStmt`（不带 `!= 0` 判断），
`optional` 与 oneof 成员共用它；普通字段仍走带判断的 `writeEncodeField`。

### 描述符侧必须「合成 oneof」

protobuf 规范要求 `proto3_optional` 字段的 `oneof_index` 指向一个**合成的** oneof
（名字 `_<字段名>`），否则 protoreflect 会判定描述符非法。实现：

1. 真实 oneof 按解析顺序占 `0 .. oneofs.len-1`；
2. `optional` 字段在这之后依次占位（`syntheticIndex()` 按字段出现顺序算序号）；
3. 每条 `optional` 字段额外写 `DescriptorProto.oneof_decl`（名字 `_<字段名>`）与
   `FieldDescriptorProto.proto3_optional = 17`。

`grpcurl describe` 的实测输出证明这套是对的 —— 它显示 `optional int32 opt_value = 15;`
而**不显示**那个合成 oneof（protoreflect 会把合成 oneof 隐藏）：

```
oneof payload {
  string text = 13;
  .echo.BumpResponse rich = 14;
}
optional int32 opt_value = 15;
optional string opt_name = 16;
```

如果只设 `proto3_optional` 不合成 oneof，protoreflect 会报描述符非法；
如果合成 oneof 但忘了 `proto3_optional`，`describe` 会把它显示成普通 oneof（语义全错）。

### 口径：与 protoc 一致

`import "common/types.proto"` 按 **root 文件所在目录**解析（等价于单一 `-I <root 目录>`），
不是「相对引用方目录」（那是 C 的 `#include ""` 语义）。所以 `common/base.proto` 里的
`import "deep/x.proto"` 指向的是 root 目录下的 `deep/x.proto`，不是 `common/deep/x.proto`。

反射里的 `FileDescriptorProto.name` 用**相对 root 目录的路径**，即 import 语句里写什么就是什么 ——
客户端 `file_by_filename` 传什么都能对上。

- `Loader.init(alloc, io)` + `loadRoot(path)` → `Loaded{ files }`
